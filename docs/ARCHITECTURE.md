# Contactor: how the app is built and what it does

The architecture and design of Contactor: what the app does and how it is built. How to work in this repository is in `AGENTS.md`.

---

## Architecture

```
Phone ──▶ the way in the setup guide chose
            ├─ Only on this network: the address of the machine the app runs on
            ├─ Cloudflare: <your hostname> ──HTTPS──▶ Cloudflare Access ──▶ Cloudflare Tunnel
            │               ──▶ cloudflared, started by the app in its container ──▶ http://contactor:8080
            └─ Tailscale: https://<name>.<tailnet>.ts.net, only on your Tailscale network ──▶ Tailscale Serve
                            ──▶ tailscaled, started by the app in its container ──▶ the app's address for Serve
                                                         │
                                              Contactor.Web (Blazor Server, .NET 10)
                                              the chosen sign-in checks every request
                                                 │                    │
                                           SQLite (WAL)        TCP :9760 ──▶ VM201
```

- **Never on the internet directly.** No port is opened to the internet. People reach the app through the way in chosen in the setup guide (`Installation.AccessType`), and every request goes through the sign-in chosen there (`Installation.SignInType`, see [Identity](#identity-sign-in)).
  - "Only on this network" (`local`, `LocalNetwork`): runs nothing. People open the address of the machine the app runs on, so the app is as private as that network. Its only sign-in is "No sign-in". The app answers only requests from this network (`ThisNetwork`, see [Identity](#identity-sign-in)), so a machine with a public address, such as a cloud server, doesn't put it on the internet.
  - "Cloudflare" (`cloudflare`, `CloudflareTunnel`): Cloudflare Tunnel on the installation's own hostname. Its only sign-in is "Cloudflare Access".
  - "Tailscale" (`tailscale`, `TailscaleNetwork`): Tailscale Serve over HTTPS, only for phones and computers on the installation's Tailscale network; nothing is public. Its only sign-in is "Tailscale identity".
  - A new way in is a class of its own and one line in the catalogue.
- **Ways in** (`Features/Access`): `IAccessMethod` runs one, e.g. keeps a tunnel open. `AccessCatalogue` lists each `AccessMethod`: its id, name, description for the guide, and the sign-ins it works with. `AccessChoice` reads the saved one at start and saves the guide's choice (`ChooseAsync`), which is used at once. `AccessHostedService` keeps the chosen one running; a new choice stops the old one and starts the new one. Nothing runs before one is chosen.
- **Sign-ins** (`Features/Identity`): `ISignInMethod` tells who made a request. `SignInCatalogue` lists each `SignInMethod`, and `SignInMethod.Create` gets the `ISignInMethod` registered (keyed) under its id. `SignInChoice` reads the saved one at start and saves the guide's choice (`ChooseAsync`). `SignInMiddleware` checks every request.
- **Cloudflare** (`Features/Cloudflare`): what only Cloudflare has. The tunnel (`CloudflareTunnel`, `CloudflaredProcess`), Access (`CloudflareAccess`, `CloudflareAccessTokenValidator`, `CloudflareAccessKeys`) and their settings (`CloudflareSettings`, `CloudflareMethods` for their ids).
- **Tailscale** (`Features/Tailscale`): what only Tailscale has. The network (`TailscaleNetwork`, `TailscaleProcess`), identity (`TailscaleIdentity`) and their settings (`TailscaleSettings`, `TailscaleMethods` for their ids).
- **Programs the app runs itself** (`Features/Access`): `KeepRunning` starts one again with a growing wait (1 s doubling to 1 min) whenever it stops, from the first wait again after a run of 5 minutes; `ChildProcess` runs one and stops it: on Linux and macOS it asks it to stop (SIGTERM), so it can save its state, and kills it with everything it started if it hasn't stopped after 5 s (`ChildProcess.StopWait`); on Linux it also kills what the program had started when it was asked to stop, if that still runs once the program has stopped (from `/proc`). On Windows it kills it with everything it started at once. It waits for the program itself to exit, not for its output to end, and then reads its output for at most 2 s more (`ChildProcess.OutputWait`), so something it started that keeps its output open never holds up the stop: stopping takes at most 7 s, within Docker's 10 s. The image has no shell or process manager.
- A saved way in or sign-in that the catalogue doesn't have stops the app at start.
- The app runs in a container and listens on port 8080 on all of the container's addresses. With Cloudflare as the way in, it starts `cloudflared` itself with the tunnel's token, and starts it again whenever it stops (`KeepRunning`). Without a token it waits for one, and a new token starts it again at once. The token comes from the setup guide (`CloudflareSetting`), else from `Tunnel:Token`. It goes to `cloudflared` only through its environment and is never logged. With Cloudflare the port is **never published** on the machine the app runs on, so nobody on the LAN can get around Access. Only the Aspire run, for development, publishes it on the developer's computer.
- With Tailscale as the way in, the app starts `tailscaled` itself (`KeepRunning`), without root or a network device (`--tun=userspace-networking`), with its state, socket and log settings in `/data/tailscale` (`TS_LOGS_DIR`), so the app stays on the Tailscale network after a restart. It sends no logs to Tailscale and keeps none on disk (`--no-logs-no-support`), so Tailscale's support can't look at them; what it writes goes to the app's log.
  - **Joining:** while `tailscale status --json` says `NeedsLogin`, it runs `tailscale up --reset` once with the saved auth key and name. The key goes to `tailscale` in a file of its own (`--auth-key=file:…`, readable by the app's user only, deleted right after), never on a command line, and is never logged or shown. A key Tailscale refuses is not tried again until a new one is saved; one that timed out is tried again. Only the first join needs the key.
  - **Serving:** once it is `Running`, it sets the name (`tailscale set --hostname`) and runs `tailscale serve --bg --https=443 http://<address for Serve>`. Serve counts as working once `tailscale serve status --json` shows the app. HTTPS needs MagicDNS and HTTPS Certificates turned on for the Tailscale network; until then `tailscale` gives a link to turn it on, and the setup guide shows it as a link ("Open Tailscale to turn on HTTPS", in a new tab; only an https address on `login.tailscale.com`), saying to leave Funnel off.
  - **The app's address for Serve** (`Tailscale:ServeAddress`; the image sets `127.0.0.2:8081`): the app listens on it next to port 8080 (`ListenForTailscaleServe`), and Serve passes requests there. In userspace mode, tailscaled passes connections from the Tailscale network to any port on 127.0.0.1, past Serve, but never to 127.0.0.2, so only Serve reaches it; the `Dockerfile` says to check that again whenever Tailscale is raised. That also reaches port 8080, `/healthz` and `/setup/reload` included, so the guide says to let devices reach the app only on port 443 in the Tailscale network's access controls. Serve's proxy connects from 127.0.0.1 too, so those two don't answer a request on Serve's address (`ThisMachine`). The address must be an IPv4 loopback address other than 127.0.0.1, 127.0.0.0 and 127.255.255.255, or the app doesn't start. Not a socket file: Serve passes requests to one only for root, or an operator who may run `sudo`. It assumes the app's container has a network of its own (not Docker's host network) and the app advertises no routes and is no exit node.
  - **A new auth key** joins again even when tailscaled is on a network already (`--force-reauth`); a new name only renames. The guide says to use a key that isn't ephemeral, and to turn off key expiry for the device, or it leaves the network after Tailscale's key expiry (180 days unless changed). A device waiting for approval (`NeedsMachineAuth`) shows that in the guide.
  - **Status:** every 10 s it reads `tailscale status --json`: the state and the app's address there (`Self.DNSName`), which the setup guide shows and sends people to. New settings start `tailscaled` again at once.
- **Cloudflare Access** (one-time PIN by e-mail, session length 1 month, an allow list of e-mail addresses) is set up in Cloudflare. Each installation has its own Access team domain (`<team>.cloudflareaccess.com`) and application; the AUD tag is in Zero Trust → Access controls → Applications → Edit → Additional settings.
- Give the Pi and the VM201 DHCP reservations in the router, so their addresses don't change.

## Boards (`Contactor.Boards`)

The app talks to a relay board only through `IRelayBoard`, `IBoardConnection` and `IBoardTraffic`, and knows its model from the board catalogue, so another make of board needs its own project with those adapters, a reference from `Contactor.Web` and a line in the catalogue, and nothing else changes. The database has a row per board (`Board`), and the app runs one live board per row (`BoardRegistry`), each with its own safety services (below). The Relays, Events, Debug and Settings screens, the Relay, Group and Input screens and the tab bar's toasts show every board; the setup guide sets up the first, and "Add a board" in Settings adds more (`BoardNew`, the guide's board steps).

- `IRelayBoard`: `Capabilities`, `State`, `StateChanged`, `AnalogChanged`, `OwnRulesChanged`, `PowerOnChanged`, `TurnOnAsync`/`TurnOffAsync(ChannelMask)`, `PulseAsync(ChannelMask, TimeSpan)`, `TurnOffOwnRulesAsync`, `SetPowerOnAsync` and `RefreshAsync`. Commands go at once or throw `BoardNotConnectedException`; they are never queued. A command returns the relays the board took: all of them on a board that takes a mask at once (the VM201, the VM204), and on one that switches a relay per request (the VM208, the Waveshare and the Devantech boards, the smartDEN, the DAEnetIP2 v2, the ADAM modules and the Shelly devices) those it confirmed: not refused, and with an answer the app could read. One that took none throws. A command isn't confirmed by its return: the next `StateChanged` is the confirmation.
- **An analog value alone is no state change.** `AnalogChanged` comes when only the analog readings changed, never `StateChanged`, so the safety services, which listen only to `StateChanged` (the interlock, the recorder, auto-off and the input actions), are never woken by a value that moves a little on every reading. A change that comes with a relay, an input or the connection comes as `StateChanged`, whose state carries the readings too, so whoever shows them listens to both. A board without analog inputs never raises it (the interface's default); `LiveBoard` passes on its current model's, as it does `StateChanged`. A polled board gets it from `BoardPoller`: when its comparer says nothing changed but the reading differs, the poller calls `IPolledBoard.OnReadingChanged` (by default nothing) instead of `OnStateChanged`, under the same lock and generation check, so an answer from before `Forget` is dropped as well. The VM204 reads its analog input with every status; the Devantech ETH1610 (16, one 0x34), ETH484-B (4) and ETH8020-B (8, a 0x32 each, before 0x24 and 0x25) and the DAEnetIP2 v2 kits (8 on P6, an SNMP get each, before the ports) read theirs on every poll, before the relays, so the relays a poll reports are the freshest, and never in a command's read (which keeps the last poll's values). An analog failure never fails the poll and never blocks "connected": a late, short, refused or out-of-range analog answer leaves the relays and inputs as read, gives each analog input "no reading" for that poll, is said on the Debug screen and in the log, and the analog inputs aren't asked for again for a minute (`DevantechClient.AnalogRetryInterval`, `DaenetIp2Client.AnalogRetryInterval`) or until a new connection.
- **A board's own rules** (issue #497): rules on the board itself that switch its relays without the app, such as the VM201's timer programs. Every model states in its capabilities what the app can know about them (`BoardCapabilities.OwnRules`, an `OwnRulesAbility`): `None` (it has none, and the app can tell: the VM204, the Waveshare 8CH, 16CH and 30CH), `ReadsAndTurnsOff` (the VM201, the Waveshare (B) and (C)), `CantTell` (the VM208, the Devantech boards, the smartDEN, the DAEnetIP2 v2 and the ADAM modules), or, for the Shelly devices, `Reads`, `TurnsOff` and `MayHaveUnseen` together (`ShellyApi.OwnRules`: the app reads and turns off their schedules and auto-on, but can't see their scripts, webhooks, auto-off or inputs); null, which no model in the catalogue has, means "can't tell" (`OwnRulesOrCantTell`). A board that reads them reports them in `BoardState.OwnRules` (an `OwnRules`: each `OwnRule` a relay and a kind, `Timer`, `InputLinkage`, `InputToggle`, `InputEdge` or `AutoOn` (the board turns the relay on again by itself some time after it goes off, e.g. the Shelly's auto-on); empty when it has none, null when it can't read them or hasn't yet), kept while disconnected. A change in the rules alone comes as `OwnRulesChanged`, as an analog value comes as `AnalogChanged`, and `LiveBoard` and `BoardRegistry` pass it on the same way. `TurnOffOwnRulesAsync` turns off the rules given, only on a person's press, never on the app's own accord: at once or `BoardNotConnectedException`, never queued; `ArgumentOutOfRangeException` before anything is sent for a relay or kind the board doesn't have; a rule given twice is taken once; it returns the rules the board took and throws when it took none, and the next state confirms it. **Rules that go together** (issue #532): turning off a rule may also remove other rules on the board, e.g. a schedule on the board that switches relays 1 and 2. A board says what lies behind its rules: `new OwnRules(rules, units)`, each unit one thing on the board (such as a Shelly schedule) with the rules it makes, every one of them one of the board's rules (`Units` reads them back). Turning off a set of rules turns off every unit that holds one of them, and a rule not asked goes too once every unit that holds it is off: `GoesWith(rules)` gives exactly those, each once in the board's order, for any set, and `GoesWith(rule)` for one. Schedule A switching relays 1 and 2 and B switching 2 and 3: relay 1's timer alone takes nothing with it, relays 1 and 3 together take relay 2's. A rule in no unit stands alone, and a board that gives no units (every board but the Shelly devices) has rules that all stand alone. `TurnOffOwnRulesAsync` still returns only the rules asked that the board took; the rules that went with them are gone from the next state. Two `OwnRules` are equal only with the same units. A board that can't turn them off throws `NotSupportedException` (the interface's default). The VM201 reports its timer programs (byte 2 of every `CMD_STATUS`) as a `Timer` rule per relay, in relay order, from its first status on. Since it raises `StateChanged` for every status, the keep-alive's too, its rules always come with `StateChanged`, and it never raises `OwnRulesChanged`. It turns off the timers asked for with one `CMD_TMR_DIS` holding only their relays' bits (relays 3 and 5: `0x14`). The Waveshare (B) and (C) report their relays' control modes (registers 0x1000–0x1007, relay n's tied to input n): mode 1 (linkage: the relay follows its input, and the board ignores commands for it) is `InputLinkage`, 2 (toggle: an input pulse flips it) `InputToggle`, 3 (edge: each input change flips it) `InputEdge`, and 0 (normal) no rule. The client reads them (FC 03) at the first reading on each connection and then every minute (`WaveshareClient.ModesInterval`, on `TimeProvider`), never writes them on its own, and gives null rules when the read is refused, unreadable or holds a mode the manual doesn't name. Its poller compares only the relays and inputs (`WaveshareStatus.SwitchesComparer`), so a change in the modes alone comes as `OwnRulesChanged` and never wakes the safety services. It turns one relay's mode back to normal with one FC 06 writing 0 to that relay's register, never FC 10 over all 8, and reads the modes back in the same command. The Shelly devices report a `Timer` rule on each relay an enabled schedule switches (`Schedule.List`: `Switch.Set`, `Switch.Toggle`, `Switch.SetAll` and `Switch.SetMany` in its calls), with one unit per schedule, so `GoesWith` is exact, and an `AutoOn` rule on each relay whose switch has `auto_on`, its own unit. The client reads the schedules at connect and when `sys.schedule_rev` changes (every minute while that can't tell), and `auto_on` with the power-on states, never in the read that confirms a switch. A read that fails makes the rules null and never makes the device lost. A change of the rules alone comes as `OwnRulesChanged`. It turns a timer off with one `Schedule.Update {id, enable:false}` for every enabled schedule behind it as last read, never deleting or rewriting a schedule, and an auto-on with one `Switch.SetConfig` holding only `auto_on:false`, and reads them back in the same command (see its README). `BoardState.Unavailable` is the relays with an `InputLinkage` rule: the board controls them by itself (see The board's own rules).
- **A relay's state after a power cut** (Issue #516): what a relay does by itself when the board gets power back, before the app runs (`PowerOnState`: `Off`, `AsBefore`, `On` or `FollowsInput`, the relay following its input). The board and the Raspberry Pi often get power back together, and until the app reaches the board its interlock can't act, so a board that turns a group's lower step on by itself can start the heat without the fan. A model states in its capabilities which states it has, and whether each relay has its own or one is for the whole board (`BoardCapabilities.PowerOn`, a `PowerOnAbility`: `States`, `PerRelay`, `Has`); null means "can't tell", and only the Shelly devices have one today (all four states, per relay; they read them at connect, in a poll when `cfg_rev` changed, and every minute while `cfg_rev` can't tell or after a failed read (`ShellyClient.SettingsInterval`), never in the read that confirms a switch, and a failed read makes a relay's state unknown without failing the poll). A board with it reports each relay's state in `BoardState.PowerOn` (a `PowerOnStates`, one per relay, null for a relay it couldn't read; null before it reported them), kept while disconnected. A change in them alone comes as `PowerOnChanged`, as the own rules come as `OwnRulesChanged`, and `LiveBoard` and `BoardRegistry` pass it on the same way. `SetPowerOnAsync(relay, state)` sets one relay's (or, for the whole board, every relay's), only when a person saves it, never on the app's own accord: at once or `BoardNotConnectedException` (also when the board doesn't take it), never queued; `ArgumentOutOfRangeException` before anything is sent for a relay or a state the board doesn't have; the board reads it back, and the next state confirms it. A board without the ability throws `NotSupportedException` (the interface's default). The Relay screen shows and sets it (see Screens), and a group's relays are always `Off` (see Relay groups).
- `PulseAsync` turns the relays on, and the board itself turns them off again after the length, also when the app stops in between. It goes like an ON: at once or not at all, never queued, and on a per-relay board it returns the relays the board took. It throws `NotSupportedException` on a board without a pulse (the VM204 and the VM208, issue #182, the DAEnetIP2 v2, the ADAM modules and the Shelly devices), and `ArgumentOutOfRangeException` for a length the board can't do, both before anything is sent. On the VM201 that includes a length its CMD_PULSE can't send exactly, such as 100 s, which its `PulseAbility.CanDo` refuses too (see its README).
- `BoardState`: `IsConnected`, the relays and digital inputs that are on, `LastContactUtc`, `Problem`, and `Analog`: what the analog inputs last read (`AnalogReadings`, one count per input, null for an input without a reading), kept while disconnected; null for a board without analog inputs or before it answered; and `OwnRules`, the board's own rules, and `PowerOn`, each relay's state after a power cut (see above). The board is the source of truth; the app never stores relay state.
- `ConnectionProblem`: why a board refused the connection on purpose, so the screens can say more than "no answer". `WrongModel` (with the model expected and, when the catalogue has it, the model found; for the same kind of board with another number of relays also `FoundRelayCount`, and the screens then name the counts: "The board at this address has 4 relays, not 2.", and in Settings "Add it again with 'Add a board' and choose the one with 4 relays, then remove this one."), `LoginNeeded` (the board asks for a login or a password and the app has none), `LoginRefused`, `FirmwareTooOld` (with the oldest version the app takes, `MinFirmware`, when known: "Update it to 1.7.0 or later on the board's own web page."), `CoverProfile` (the board is set up to drive a cover, not relays: "Set its profile to \"switch\" on its own web page, then check again.", with "Check again" in the setup guide, not "Choose model") or `AskedToWait` (the board asks the app to wait a while, after wrong logins or with too many clients at once; it doesn't say which, so the words don't claim a wrong login: "The board asks Contactor to wait a while. If you just changed the password, check it."; the poller tries again by itself after 10 minutes). `IsAboutLogin` is true for `LoginNeeded` and `LoginRefused`: the screens then open the login fields. `AskedToWait` leaves them as they are. The Devantech boards report the first three, the VM201 and VM204 the two about the login, and the Shelly devices all six (`WrongModel` for a Gen1 device and another number of relays, `CoverProfile`, `FirmwareTooOld` before 1.7.0, `AskedToWait` for an HTTP 429); the VM208, Waveshare, smartDEN, ADAM and DAEnetIP2 v2 can't tell, and report none. It never holds a secret. It is cleared at the board's first answer, at a new address, at a new login, and by a connect that fails for another reason, such as no answer. A polled board's client says why through its exception (`IConnectionProblemSource`), which `BoardPoller` reads from a failed connect.
- `BoardCapabilities`: how many relays and inputs, its analog inputs (`Analog`, an `AnalogAbility`: how many, the converter's highest count and the voltage it means, e.g. 1023 = 6.6 V on the VM204, 5 V on the ETH1610 and ETH8020-B and 3.3 V on the ETH484-B and the DAEnetIP2 v2 kits; null without any; `AnalogInputCount` counts them), whether the board reports changes by itself, and its pulse, `Pulse` (a `PulseAbility`: shortest, longest and step, and for a board whose lengths those can't say exactly, `Exact`, which `CanDo` also asks), or null without one. The VM201 pulses for 1 s to 99 h in steps of 1 s, only the lengths its CMD_PULSE can send exactly (`Exact`), the Devantech boards for 0.1 s to 25.5 s, the Waveshare boards for 0.1 s to 3276.7 s and the smartDEN for 0.1 s to 6553.5 s, all in steps of 0.1 s. The DAEnetIP2 v2 kits have none: the board documents no pulse of one relay over SNMP. Nor do the ADAM modules: their pulse output is a pulse train set up in registers. Nor do the Shelly devices: the app uses only `Switch.Set` with `id` and `on`.
- `BoardPoller<TReading>`: the loop for a board that doesn't report changes by itself (the VM204, the VM208, the Waveshare and the Devantech boards, the smartDEN, the DAEnetIP2 v2, the ADAM modules and the Shelly devices). The board's own code implements `IPolledBoard<TReading>` (connect, e.g. log in; read the state once); the poller asks every `PollInterval` (2 s) with `TimeProvider`, refreshes `State` (and so `LastContactUtc`) on every poll but reports a state only when it changed (a comparer decides what counts), counts the board as lost after `FailuresBeforeLost` (3) failed polls in a row (a failed command counts as one, so a dead or broken board is lost even while commands keep coming), and connects again with backoff 1 s → 30 s. A connect the board refused on purpose isn't tried again in that loop (Issue #522): each try may count toward the board's lockout, such as a Shelly's brute-force protection, and the same login gets the same answer. After `LoginRefused` for a login that never connected since the last `Restart` (a new address or login), the poller sends nothing more (the step `Held`, with no timer) until a new address or login (`Restart`) or a person's "Check again" (`TryAgain`). A login that connected before, which the board may refuse for a while (e.g. while it restarts), is tried once every `AskedToWaitPause` (10 minutes) for `RefusedLoginRetries` (24 hours) from the first refusal, and then held the same way. A connect that works ends it, and the 24 hours start over at the next refusal. "Check again" keeps them: it is the same login. The problem shown stays "wrong password" the whole time. After `AskedToWait` it waits `AskedToWaitPause` (10 minutes, longer than a Shelly counts wrong passwords for) before one attempt, or less on "Check again" or a new login: a 429 may also come with too many clients, when the password is right, so it doesn't stop for good. `LoginNeeded` and the other problems keep the usual backoff. `TryAgain` does nothing while the board is connected. The VM201 isn't polled and keeps its own loop. Commands go through `RunCommandAsync`: a poll under way is cancelled (that doesn't count as a failure) so the command goes at once, it throws `BoardNotConnectedException` once the board is lost (decided under the same lock as the polls), and what the command returns, the board's state right after it, is taken as a poll's answer. The smartDEN, DAEnetIP2 v2, ADAM, Waveshare, Devantech and Shelly clients switch one relay per request and then read the board's state, through `RunSwitchesAsync`. When that read fails, the command still succeeds, with a `CommandReading` that holds no reading. That isn't an answered poll: `State` keeps its last reading and `LastContactUtc`, the failed polls in a row aren't started over, and the board is read at once. The VM208 also switches one relay per request, but each answer is a status the board read, so it goes through `RunCommandAsync`. A command fails as a poll would: whatever it throws (unreadable or no answer) counts once, except a cancellation by the caller, `BoardNotConnectedException`, with which the command says it sent nothing (the VM204 logging in again), and `BoardRefusedException`, with which it says the board answered but refused every relay in it (a Waveshare, smartDEN or ADAM exception answer, a DAEnetIP2 v2 error-status, a Devantech `01` or a Shelly error frame such as -109 "Overtemp condition present"). A refusal starts the count over, as an answered poll does, so quick commands the board refuses never lose it. A failed command is followed by a read at once, so the screens show what the board really did; that read is an ordinary poll that counts on its own, so a dead board is lost after 3 unanswered requests in a row. Outside `RunCommandAsync` the boards still throw `BoardNotConnectedException` ("didn't take the command") for a refusal. `PollNow` asks at once, `Restart` ends the connection or wait (new address or login) and clears the problem, `TryAgain` does the same only while not connected (`IBoardConnection.TryAgain`, which the Shelly, VM204 and Devantech connections pass on, and the others, which never hold, ignore), and `Forget` (a new address) resets the state to "never answered" and drops an answer from before still on its way. A connect's problem is dropped when `Forget` or `Restart` came after the connect started; the same problem again raises no new state. Disposing it (`DisposeAsync`, when a board is removed or the app stops) stops new work at once: the run ends, and a command after it, or one still waiting for the lock, throws `BoardNotConnectedException`. It then waits for the work under way, at most `DisposeWait` (15 s), before the board's code closes its connection; a command that outlasts the wait throws `BoardNotConnectedException`, whatever the closed connection makes it throw, and a client opens no new connection once disposed.
- `ChannelMask`: a set of channels (relays or inputs) numbered from 1, at most 64; bit 0 is channel 1.
- `IBoardConnection`: where the board is (`BoardEndpoint`) and its login (`BoardLogin`), with the defaults from the board's own settings, changeable while the app runs; `CheckLogin` says what the board can't take, and `RunAsync` keeps the connection open.
- `IBoardTraffic`: each step on the connection as a `BoardTraceEntry` in plain words (direction, text, the bytes, error, routine), for the Debug screen and the toasts. The board writes the words and never puts a password in one.
- **The board catalogue** (`Features/Boards/BoardCatalogue`): every model the app supports, as a `BoardModel` (id, brand, name without the brand, capabilities, default port, login length, an optional login hint (`LoginHint`, which the app puts in words), whether the login is a password alone, `PasswordOnly`, and whether the board always has one, `LoginRequired`) and how to build it while the app runs (`ActiveBoard`: its adapters, what only it has, and its own small set of services).
- **One live board per board's row** (`Features/Boards/LiveBoard`): that board's `IRelayBoard`, `IBoardConnection` and `IBoardTraffic`, the same object for the board's whole life, passing everything to its model (`LiveBoard.Active`, an `ActiveBoard`). It has its own connection loop (each model's run first takes the address and login saved on its row, waits while it has no address, starts what only the model has, then its connection) and its own Debug trace (`LiveBoard.Trace`, a `BoardTrace`, kept when the model is replaced). Before its model is chosen it has no relays and never answers: commands throw `BoardNotConnectedException` and nothing connects. A new model (`LiveBoard.ReplaceAsync`) stops the old model's connection and what only it has, starts the new one's, disposes the old one once its run has ended, and reports the new model's state as unknown until it answers, as for a new address; nothing the old one still passes on reaches the listeners.
- **No default board, and no restart.** `BoardRegistry` (a singleton) holds every live board (`All`, `Find(boardId)`), tells each board's new state (`StateChanged`, with the board's id) and when a board is added or removed (`BoardsChanged`), and runs every board's connection (`RunAsync`, from `BoardHostedService`); a board's run that fails, or ends cancelled while the app isn't stopping (e.g. a timeout), stops the others and the app, so the container starts it again. At start it makes a live board for every row, each with its saved model (`Board.Type`), and the app refuses to start on a saved model the catalogue doesn't have. `BoardChoice` chooses the first board's model: at start the saved one, and in the setup guide the one picked there, while the app runs (`BoardRegistry.ReplaceModelAsync`, which makes the live board for a row made since start); the board takes the model's name (`BoardModel.Name`) until it has one of its own. A choice adds the rows for the board's relays and inputs first. An installation in use from before the guide chose the model (the guide done, none saved) keeps the board it ran: `Board:Type`, or the VM201, saved once at start on its `Board` row (the row without a model that the migration MoveToBoards left). One whose boards were all removed has none, as a new installation. A model is never replaced once the guide is done: replacing the board is issue #32. `AddBoards` registers the registry and what every board has in the app: its name, address and login on the Settings screen (`BoardAddressHandler`, by the board's id), adding it (`BoardRegistry.AddBoardAsync`), removing it (`BoardRemoval`), the Debugging setting and `BoardHostedService`.
- **Adding a board** (`BoardRegistry.AddBoardAsync`, from "Add a board", `BoardNew`), one change to the boards at a time (the registry's gate): a new `Board` row last in the list (`SortOrder` after the highest) with its model and a name (the one typed, or else the model's made unique: "Velleman VM201", then "Velleman VM201 2", within 40 characters, `BoardRegistry.UniqueName`), and "no address and no login" saved on it (Host "", the model's default port, Username and Password ""), so it never takes the address and login in the model's settings section, which are the first board's; this holds also for a board added when the app has none, which becomes the first board: its address is typed in the next step, and the settings' address belonged to a board that was removed (as `BoardRemoval` keeps them from the board that becomes first). Then the rows of its relays and inputs, by channel, with their runtime rows and its `BoardRuntime` (`SeedBoardAsync(boardId, …)`), and its live board, made as at start: watched by every safety service before its model's connection starts, then run (`RunAsync` runs a board added meanwhile at once). If any of it fails, nothing of it is left: its live board is taken out and its rows deleted (`BoardRemoval.DeleteAsync`). The board is unfinished (`Board.IsUnfinished`) until "Add a board" finishes it (`BoardRegistry.FinishAddingAsync`, on "Done" or "Go on without a connection"), or its address or login is saved on its page in Settings (the person sets it up there): it runs as any board, so its steps can reach it, but it isn't on Relays (`BoardRegistry.Shown`: its cards, counts, board chips and side menu), in Events' board filter or a toast's count, or offered in "New group". "Turn off all boards" still turns it off, and doesn't name it when it can't reach it. At the next start an unfinished board is removed before the boards are made (`BoardRegistry.LoadAsync`, its rows and events as `BoardRemoval.DeleteAsync` deletes them, logged), so a board left half way isn't left behind. It never runs again, so nothing is sent to it: a relay "Try" left on stays on, as the app never turns anything off at start. A board from before this (the migration AddBoardUnfinished) is finished. A model is never replaced on an added board; a different one is a new board.
- **Removing a board** (`BoardRemoval`, from its page in Settings), one removal at a time: from the person's confirm the board is closed to every new ON (`LiveBoard.CloseAsync`: `TurnOnAsync` and `PulseAsync` throw `BoardClosedException`, a `BoardNotConnectedException`, "The relay board is being removed."), so no tap, schedule, input action (from any board) or group start can turn one of its relays on, and the removal waits for every ON already on its way (`LiveBoard` counts them) before it looks at the board. OFFs still go through, and so does a stopping group's run-on (after a trip, the relay above the gap: `LiveBoard.TurnOnForRunOnAsync`, only from the group sequencer), since an ON above a gap never breaks the interlock and a heater must not be left without its fan. What was refused isn't lost should the removal be called off: a schedule's ON is tried again at the next tick while its window runs (only that one: it isn't a reconnect, so nothing else is reconciled), and an input's actions are done again once the board opens again (`LiveBoard.Reopened`) if the input is still as it was. A board that answers then has its relays turned off: "All off" for that board (`RelayControl.TurnAllOffAsync`), its groups stopping in their order with their run-on times, and "All off" again every half second while anything is on (`RelayControl.TurnAllOffAgainAsync`, which logs no "Off": only the first "All off" does). Once the board shows every relay off and no group is stopping (looked at under the group sequencer's lock, so no step is half done), within 10 s, it is removed. A group still running on, or about to (a stop's step not confirmed yet), when the 10 s are up, or whose run-on ends after them, stops it: nothing is removed, the board is opened again (`LiveBoard.Reopen`) and works as usual, and the page says when the whole group is off (the run-on under way and every one above it): "Fan heater – Lathe runs on until 14:32. Remove Garage when it's done.". If it loses contact meanwhile, or a relay won't go off, nothing is removed either and the page says so. A board without contact is removed as it is, when the person was told so (`turnOffFirst`); one the person was told would be turned off first that has lost contact since isn't removed. To remove it, `BoardRegistry.RemoveAsync` takes its live board out of `All` (nothing new is sent to it), disposes it (a step under way finishes, its watches end, then its connection; its run ends quietly) and raises `BoardsChanged`; `LoadAsync` leaves it out from then on. Then everything about it is deleted in one transaction, its events included (see the data model). The same transaction logs who removed it, as an event with no board so it stays: "John removed relay board Garage (Velleman VM204)", with the board's name and model as they are at the delete saved in the event, since the board's row is gone; the deletes and the event are saved together or not at all. "Cancel" on "Add a board" takes its board out the same way but logs nothing (`BoardRemoval.CancelAddingAsync`): that board was never added. If the delete fails, nothing is deleted, the board runs again in its place in the list (`BoardRegistry.RestoreAsync`, by `SortOrder`), and the page says "Couldn't remove Garage. Nothing was removed.". A command for one of its relays after its rows are gone fails as for a relay or board that isn't there (`RelayControl` turns a failed save for a removed board into `BoardNotConnectedException`). Someone removing it a second time is told "This relay board was removed already.". The board itself isn't changed. The last board can be removed too: the app then runs none, as a new installation before the guide chooses one: nothing connects, commands throw `BoardNotConnectedException`, Relays and Settings say "There's no relay board in Contactor." with "+ Add a board", `/healthz` stays healthy with no boards, and the setup guide isn't opened again (it stays done).
- **A board's address and login:** the ones saved on its row (`Board.Host`, `Port`, `Username`, `Password`) or, until some are saved, its model's settings. The address and login in the model's settings section (`Vm201:Host`, `Port`, `Username` and `Password`, e.g. from environment variables) are the first board's only, the one the setup guide set up; any other board starts at the model's default port with no address and no login until some are saved for it, and takes the rest of the section like the first (`BoardSetup.Settings`). A board added in the app has "no address and no login" saved from the start, so it never takes them, also when it is or becomes the first. `BoardCatalogue`'s `Create` takes the board's `BoardSetup`: its id (what only the model has logs its events with it), whether it is the first, and its saved address and login.
- **Safety per board.** Every safety rule holds for each board on its own. Each live board is watched (`IBoardWatcher`) from the moment the registry makes it, before its connection starts, by its own part of each safety service: its auto-off (from `AutoOffService`, which listens to no status: it reads the board's state at each check), then, in this order so the interlock comes first on every status, its group sequencer (`BoardSequencer`, from `GroupSequencer`), its event recorder (`BoardRecorder`, from `BoardEventRecorder`), its inputs' actions (from `InputActionService`, which listens to no status either: it gets its inputs' changes from the recorder, through `InputChangeFeed`, on a queue of its own) and its scheduler (`BoardScheduler`, from `SchedulerService`). Each has its own state, lock and loop, and finishes what it is doing (a step, a tick, a check, an input's action) before its watch ends, so nothing is sent to a board being disposed; the services run every board's loop while the app runs (`BoardParts`), also for a board made later, so a board that is lost, slow or failing (a command that doesn't finish) holds up nothing on another: not its interlock, its events, its minutes, its auto-offs or its inputs' actions. The boards' connections start only once every hosted service has started (`BoardHostedService` waits for `ApplicationStarted`), so these loops run before the first status and every status is handled in order; a board made while the app runs (the setup guide's, or one added in Settings) is watched before its connection starts in the same way. Each live board also has its own expected changes (`LiveBoard.Expected`). The live board owns its watches and ends them (unsubscribed, loops stopped) when it is disposed, before its connection. `RelayControl` stays one for the app and goes by the relay's own board (`Relay.BoardId`, then the channel on its row); a command for a board that isn't connected, or that the app doesn't run, throws `BoardNotConnectedException` and nothing is queued. A handler checks a relay or an input against its own board (`BoardRegistry.HasRelay`, `HasInput`).
- **Every screen goes by each board.** The Relays, Relay, Group and Input screens take each relay's, group's and input's own board from `BoardRegistry` and listen to `BoardRegistry.StateChanged`; Debug and the tab bar's toasts listen to every board's trace, and to each board added or removed, through `BoardTraceWatch`. Settings lists every board, and each board's page has its own name, address, login and "Remove". The setup guide works on the board it sets up, the app's first (its row id, from `BoardChoice`), and "Add a board" on the one it made.
- **Each board is described in its manufacturer's `Contactor.Boards.<Manufacturer>/README.md`:** its protocol or routes, its client and simulator, and what to check on a real board. Read it before you change that board. Only the VM201 has run on a real board; every other model, the DAEnetIP2 v2 kits included, is built from its manual and not yet tested on a real board (the README's board table says so).
- **Adding a model:** one project per manufacturer (`Contactor.Boards.<Manufacturer>`, e.g. `Contactor.Boards.Velleman` for the VM201, VM204 and VM208) with its `IRelayBoard`, `IBoardConnection` and `IBoardTraffic`, a `<Model>Boards.Create` in `Features/<Model>` that builds it with what only it has, one line in the catalogue, and a `README.md` that describes the board. Nothing else in the app changes.
- `ISimulatedBoard`: a fake board of a model for development and tests, on a local port (TCP, or UDP for the DAEnetIP2 v2's SNMP): its relays, inputs and connected clients, a relay switched, an input set or an analog input set (`SetAnalogAsync`, in counts; `SimulatedBoardState.Analog`, empty for a board that doesn't simulate any) "at the board", dropped connections, a change event, and the traffic as `BoardTraceEntry` from the board's side (`Sent` is still from the app to the board). A model with timer programs of its own also implements `ISimulatedBoardTimers`: all of them at once, or one relay's at a time; one whose relays have control modes of their own (the Waveshare (B) and (C)) implements `ISimulatedBoardRelayModes`, one relay's mode at a time, and the simulator's page has a select per relay. A simulator with a pulse carries it out on its own `TimeProvider` (`SimulatedPulses`): the relay goes back with no further command from the app, a later pulse of the relay starts it again, and switching the relay ends it. Each manufacturer's project brings its own simulators (`Vm201Simulator`, `Vm204Simulator`, `Vm208Simulator`, `WaveshareSimulator`, `DevantechSimulator`, `SmartDenSimulator`, `DaenetIp2Simulator`, `AdamSimulator`, `ShellySimulator`).
- What only one board has stays in its own project and its `Features/<Board>` folder, and runs only while that model is the board's (`ActiveBoard.Extras`, started before its connection and stopped with it, and logging its events with the board's id). No model has any today: the Waveshare (B) and (C) relay modes, which `WaveshareRelayModesService` used to set to normal at each connection, are now the board's own rules (issue #497).
- The database holds one relay per relay on the board (`IRelayBoard.Capabilities.RelayCount`, at most 64) and one input per digital input (`InputCount`), seeded at start and when a board is chosen, each found by its channel. Rows whose channel is above the count, left from a board that had more, are kept but not shown, offered or switched.
- **A relay's id is not its channel.** `Id` is only the database's key (links, events, runs, schedules, groups); `Channel` is where it is on the board. Every command, every look at `BoardState` and `ExpectedChanges`, and every number on a screen goes by the channel: from the row where it is already loaded (a group's members come with their relays), or through `BoardChannels` (`Features/Boards`), which reads relay id ↔ channel and input id ↔ channel for one board from the database where it is needed, so it never goes stale. A channel only means something with its board: every look at a board's state or expected changes is that board's.

## The simulator (`Contactor.Simulator`)

A small Blazor web app for development, filling the window from 1024 px and one column that scrolls on a phone or tablet. English, like the app.
- `Simulator:Boards` lists the boards that start with it (`Type`, `Port`, optional `Username` and `Password`); none listed: one VM201 on 9760. Boards added on the page last until it stops. Each board listens on its own port on 127.0.0.1, so several run at once.
- `Simulator:AppAddress`: the address the app reaches the boards at, only shown on the page (the boards still listen on 127.0.0.1); empty: 127.0.0.1. The Aspire run sets `host.docker.internal`, where the app's container reaches this computer.
- `Simulator:MaxBoards`: how many boards may run at once; "Add a board" then refuses another ("You can have at most 20 boards."). The boards in `Simulator:Boards` always start. Not set: no limit. The demo sets it for each visitor.
- `SimulatorCatalogue`: the models it can simulate, each with its `ISimulatedBoard`. A new model is one line there.
- `SimulatedBoards` runs them; `RunningBoard` keeps each board's latest 100 traffic lines in memory, with the keep-alive left out and counted, and logs what is done on the page as "at the board".
- The page: the boards on the left with "Add a board"; the selected board's relays (a click switches one as the board's own button would), input, a slider per analog input (0 to the converter's highest count, with the voltage next to it), a checkbox per relay for its own timer, "Drop connection" and "Remove"; for a Shelly also its special cases (`ShellyControls`): asking the app to wait (429, only with a password), its firmware and profile, `Switch.Set` refused per relay, `auto_on` and `initial_state` per relay, and its schedules, each on or off, with one to add (a relay on or off every day at a time, at most 20); its traffic as a table below (time, direction, what, bytes; errors red). Each board and the header show where the app reaches it (`Simulator:AppAddress` and its port).
- Below 1024 px: the header stacks, the boards are a row of cards that scrolls sideways, "Add a board" and the traffic fold away behind a button each (no JavaScript; the page's own state), the relays four per row, and 44 px tap targets. The page itself never scrolls sideways.

- **Events are kept for one year,** fixed, with no setting (Issue #48). Every night, right after the backup, `EventRetention` removes the events from before one year ago, by `TimestampUtc` in UTC; on 29 February that is 28 February a year earlier. The nightly copies still hold them for a while. Kept also when older: the newest event the app reads back as the last of its kind (an input's newest change, a relay's newest off or pulse, the newest end of an update), so an input's state, "Off since …" and an update's event stay as they were. It removes at most 500 events per statement, each its own short transaction, with a short pause between batches, so the app's own writes get the database in between. It logs how many it removed; a failure is logged and tried again the next night.

- `PRAGMA journal_mode=WAL` and `PRAGMA busy_timeout=5000` at start. Every transaction starts as a writer (`BEGIN IMMEDIATE`, EF Core's default with Microsoft.Data.Sqlite), so a transaction that reads and then writes waits for another writer instead of failing. Never open one deferred or with `ReadUncommitted` (`PersistenceTests.Should_HoldTheWriteLock_FromBeginTransaction`).
- **SQLite stays the database.** Keep SQLite-specific code to `Persistence` (the start-up settings above) and `Features/Backup` (`VACUUM INTO`); everything else goes through EF Core, so a later switch to PostgreSQL stays a small change.
- **Relay state is not stored.** The VM201 is the source of truth; the app always shows the board's latest `CMD_STATUS`.
- Every timestamp is stored in UTC and shown in the app's `TimeZone` setting (default Europe/Stockholm). Schedules are stored as local time, see below.
- EF Core migrations: `dotnet tool run dotnet-ef migrations add <Name> --project Contactor.Web --context ContactorDbContext --output-dir Persistence/Migrations --namespace Contactor.Web.Persistence.Migrations`. The tool puts the model snapshot in a wrong folder named after the namespace; move it to `Persistence/Migrations/`. The database file is `/data/contactor.db` in the container (`/opt/contactor/data` on the Raspberry Pi's SD card). The app writes little (a row a minute from the scheduler, the time of contact every 5 minutes, the event log, a nightly backup), so a good SD card is enough; an endurance card is recommended.

## Domain rules

### Manual control
- The ON/OFF button sends `CMD_ON`/`CMD_OFF` with a single bit and logs the event with the user's e-mail.
- On a manual ON with `MaxOnMinutes` set: set `RelayRuntime.AutoOffAtUtc`.
- A command goes to the relay's own board, on its channel there, and its event has that board's id.
- **"All off"** is per board (`RelayControl.TurnAllOffAsync(boardId, …)`): it sends `CMD_OFF 0xFF` (that board's relays outside a group) and is logged as one event per relay that was actually on, a relay the app had just turned on counting as on before the board shows it (`ExpectedChanges.IsPending`); then that board's groups stop. `TurnOffAllBoardsAsync` does it on every board at once: a board without contact is skipped (nothing sent or queued for it) and reported, with every board lost on the way. On the Relays screen each board's section has its own "All off" (one tap, as with one board), and with two or more boards "Turn off all boards" asks first and then names the boards it couldn't reach.
- While a board is disconnected its buttons are disabled. Never queue commands for later. Another board's work goes on.

### Auto-off
- A `BackgroundService` checks every 15 seconds, each board on its own loop, with its own state and expected changes. When `AutoOffAtUtc` has passed and the relay is still on, it sends OFF to the relay's board and logs the event with Actor `auto-off` and Details `{"afterMinutes":120}`. A board without contact is skipped: its due relays are turned off at the first check after it is back, and another board's as usual.
- Does **not** apply to relays turned on by a schedule. There the schedule's OffTime is the end.
- **Every relay that is on gets an auto-off.** A relay on without an owner (switched at the board's own button or web page, during an outage, or after a press the board didn't confirm) gets the relay's own "Turn off automatically after", counted from when the app saw it on (`BoardEventRecorder`: on an external ON, and at start for a relay that is on with nobody's run; `AutoOffService`: at every check, for one on with nobody's run that the app didn't see come on, e.g. after an OFF the board was sent but didn't carry out). `TurnedOnBy` is `external`, and its status line reads "On since 14:02 · outside the app · off 16:02". A group on without an owner gets the group's own auto-off the same way (`GroupPlanner.GiveOwnerlessAutoOff`). During a running window of its schedule, the scheduler takes such a relay or group over (`schedule`, no auto-off), so it goes off at the OffTime. Nobody guesses who switched it.
- **A relay that is off keeps no run.** `AutoOffService` ends, at every check, the run of a relay the board shows off (e.g. one that went off while the app was down, or whose "off outside the app" gave way to another writer), so its status line doesn't keep saying "On since". Not while an ON for it is still on its way (`ExpectedChanges.IsPending`), and only the run as read (`RelayRuns.EndOutside`); nothing is logged.

### Scheduling
- A `BackgroundService` ticks every minute, on the minute.
- Times are read in the app's `TimeZone` setting (default Europe/Stockholm; `LocalClock`). **Daylight saving:** an OnTime that doesn't exist (02:xx in spring) runs at the next valid minute. An OnTime that exists twice (02:xx in autumn) runs only once.
- At OnTime ON is sent, and at OffTime OFF. Both are logged with Actor `schedule`.
- A window over midnight (OffTime < OnTime) belongs to the day it started.
- **At start or reconnect:** reconcile against the schedules. If an active schedule window is running and the relay is off, turn it on. Never turn anything *off* at start, with two exceptions: auto-off times that have already passed, and a schedule's missed OffTime for a relay **that schedule turned on** (see below).
- If two schedules overlap: ON wins (an OFF is skipped while another of the relay's schedules is running).
- **Per board:** each board has its own part of the scheduler (`BoardScheduler`), with its own progress, connect generation, reconciliation and loop, for its own relays' and groups' schedules. Each board's loop ticks every minute, on the minute, and at once when that board comes back; a board whose tick doesn't finish (a slow or hanging command) holds back only its own minutes.
- **Catch-up:** the scheduler stores the last minute it handled on each board (`BoardRuntime.LastTickUtc`). After a restart or a lost connection it handles what it missed on that board, at most 24 h back: a window that is still running is turned on, and a missed OFF is applied only if `RelayRuntime.TurnedOnBy` is `schedule`. A relay a person turned on is never turned off at start. A live tick (OffTime within the last minute) turns the relay off whoever turned it on. While a board is disconnected the scheduler does nothing on it and doesn't move its `LastTickUtc`; another board's minutes go on.
- A relay the scheduler turned on is turned off at the next tick when no running window covers it any more (its schedule was deleted, paused or moved during the run, or its OFF is older than the catch-up reaches): nothing else would turn it off.
- **A person's auto-off wins over a schedule.** A relay a person turned on keeps their `AutoOffAtUtc` even when a schedule window starts while it is on. When auto-off turns it off, the schedule doesn't turn it back on during that run; it runs again at its next OnTime. A new "Turn off automatically after" limit never gives a relay the schedule turned on an auto-off.
- A relay the scheduler turns on gets `RelayRuntime.TurnedOnBy = "schedule"` and no `AutoOffAtUtc`; its status line reads "On since 06:30 · schedule · off 08:00". An off relay whose schedule turns it on within 24 h reads "Schedule: on tomorrow 06:30".

### Relay groups
A group runs its relays in steps, in a start order, e.g. a fan heater: the fan first, then the heat; heat off, the fan runs on, then the fan off. A step holds one or more relays that switch together (step 1 "Fans": Fan 1 + Fan 2; step 2 "Heaters"), and has the wait before it starts and its run-on; a group needs 2 relays or more, in one step or more. A relay's name in the group's events and status is its step's when it is the step's only relay, otherwise its own. `GroupPlanner` has the rules (pure, tested without a board); `GroupSequencer` runs them for each board on its own (`BoardSequencer`: its own lock and loop, on every status of its board and every second), and saves `GroupRuntime`.
- **One board:** a group's relays are all on one board, the group's (`RelayGroup.BoardId`): a new group takes its first relay's board, `GroupsHandler` refuses relays on another, and "New group" only offers the first picked relay's board. Across boards is issue #204.
- **Start:** from the top, the relays of a step together. The next step only once the board's status confirms every relay of the one above is on (a status from before an OFF still on its way doesn't count) **and** its `StartDelaySec` has passed. No confirmation within 5 s: the start stops, what runs keeps running, `group-start-failed`.
- **Stop:** from the bottom, the relays of a step together. The lowest step goes off at once; each one above after its `RunOnSec`, counted from when every relay of the one below is confirmed off. "Turn off" during a run-on of one relay (below) keeps the run-on's time. ON during a run-on carries on from where the group is, restarting nothing. A relay whose ON is on its way (sent, and not yet shown by the board, e.g. one turned on again while the others of its step stop) counts as on for a stop of the whole group. It goes off in its place from the bottom, as if the board showed it on: with its step, once the steps below it are off and its step's turn has come, so nothing above it goes off first. When its step's OFF is already on its way, its OFF goes at once. The board gets that OFF after the ON, as it takes its commands in order. Its OFF counts as done only once that ON is no longer on its way and the board shows the relay off.
- **Interlock:** a relay may only be on while every relay of every step above it is (only the lowest step on may be partly on, e.g. only Fan 1). Checked first on **every** status of the group's board, whatever caused it (the app, the board's web page or buttons, its timers, a power cut), and at start and reconnect: everything below the gap goes off at once, the missing relays of the step are started so it can run on, then the group stops as usual. If one fan stops, both heaters go off. Logged as `interlock-trip` with Actor `system`.
- **One relay at a time** (on the Group screen): ON only when every relay of the step above is on ("Needs Fans to be on"). OFF turns every relay below its step off at once, then this one runs on with its step's run-on and stops; the other relays of its step stay as they are. A relay below with its ON on its way (sent, and not yet shown by the board) counts as on: its OFF goes with the others, after that ON. When it is in the step just below, this one runs on only once the board shows it off and that ON is no longer on its way. Further below, its OFF already went after its ON, and the board takes its commands in order. So does this relay when its own ON is on its way: its OFF goes after that ON, in its place, and counts as done only once that ON is no longer on its way and the board shows it off. That gives "only the fan" (or "only Fan 1") without a special mode. Both check the interlock first, as on every status: while it is broken, ON for a relay below the gap is refused ("Needs Fans to be on") and the trip goes on; ON never calls off a trip's stop while its run-on relays are on their way. A step that a stop is turning off (any stop: Turn off, auto-off, "All off", OffTime, an input, one relay's OFF, a trip), its OFF sent and not yet confirmed or due now, counts as off: ON below it is refused ("Needs Fans to be on"). A relay with an OFF on its way (sent, and not yet shown by the board) counts as off, whatever the last status still shows: ON for it sends its ON, which takes that OFF over and is waited for, and the other relays of its step still go off. During the step's run-on, ON still calls the stop off. OFF during a stop of the group (Turn off, auto-off, OffTime) keeps that stop: it never ends sooner, so the rest of the step still goes off. A relay turned off while another relay of its step is already being stopped joins that stop: it goes off with it, after the relays below and the step's run-on (at once when the step's OFF is already on its way). Turning one of those relays on again brings back that relay only; the others still go off, and nothing below their step may come on meanwhile. Its ON is logged, and their stop finishes only once the board shows it on (or its ON is no longer on its way, after 5 s): a status that shows the others off first doesn't end the run, so it isn't taken for one turned on outside the app. A stop called off by turning a relay on again gets the group's auto-off back.
- A relay in a group is only switched through its group (`RelayControl` refuses), has no auto-off or schedule of its own, and can't get a schedule while in it (its group can). A relay with its own schedules, one an input controls, or one its board controls by itself (see The board's own rules: unavailable to Contactor) can't join a group. A member its board comes to control by itself puts a red warning on the group's card and page, and the group doesn't start until it is reset. Which relays, their steps and their order, creating and deleting only change while the whole group is off.
- **Schedules:** a group has schedules of its own, run by the scheduler by the same rules as a relay's (catch-up, ON wins on overlap, a missed OFF only stops what the schedule started, a person's start and auto-off win). OnTime starts the group in its order through `GroupSequencer`, with Actor `schedule` and no auto-off; OffTime stops it with its run-on times. The sequencer logs both as `group-on`/`group-off`. A group that is already partly on at OnTime (e.g. only the fan, switched by hand) is left as the person set it, with their auto-off; the OffTime still stops it.
- **Auto-off** (`RelayGroup.MaxOnMinutes`) stops the whole group with its run-on times. **"All off"** stops each group with its run-on times and turns the other relays off at once.
- **No board:** nothing is sent or queued for it; run-on times keep counting, and on its reconnect its interlock goes first (everything below a gap goes off at once, also while a trip is already under way), then what fell due. Another board's groups run on. A command the board hadn't confirmed gets a fresh 5 s to show; the relays a stop needs for its run-on (e.g. the fans after a trip) are sent once more, then given up (`group-start-failed`) if they still don't come on. They are sent again only after the interlock, only while every step above them is still all on (a relay above may have gone off during the outage), and never a relay the same pass turns off.
- **After a power cut** (Issue #516): every relay in a group is `Off` after a power cut on its board (`GroupPowerOn`, the one place the rule is kept, pure). A board that turns a group's relay on by itself when the power comes back ("On", "As before" or "Follows its switch") does it before the app runs and without the group's start order: the heat without the fan, or both at once. So the board never starts a group's relay by itself, and the app starts the group in order once it runs. A board with one state for every relay (`PowerOnAbility.PerRelay` false) follows the same rule: `Off` for the whole board while any of its relays is in a group (the Relay screen's "Off" only). Only a state the board reported breaks the rule (`GroupPowerOn.NotSafe`): an unknown state, a board that hasn't reported its states and a board without the ability give no warning. An unknown state on a board with the ability (not read yet, or a read that failed; `GroupPowerOn.Unknown`) is set to `Off` too when a person presses "Create group", or Save for the relays it adds (`GroupPowerOn.ToSetOnSave`), but never by "Make it safe" and never without a press (the user's decision on PR #530). The group's card and page then warn, and "Make it safe" sets those relays to `Off` (`RelayPowerOnHandler.MakeGroupSafeAsync`: at once, never queued, one write for the whole board, logged as `power-on-set` with the person, a write the board didn't answer kept as unconfirmed as on the Relay screen). "Create group" and a Save that adds relays write `Off` to those of them not `Off` or unknown after the group is saved; when the board doesn't take it, the group stays saved and its warning shows (for a state that was unknown, once the board reports a state other than `Off`). The group can still start meanwhile, since the risk is at the power cut, not at the start. Nothing is written at a start, a connection or a reconnect. (The rule replaces Issue #516's first plan, where a step could be as on as the step above it: two steps on "On" would come on together, without the start delay.)
- **Safety:** the app's interlock only works while the Pi and the app run. Where safety depends on it (heat without the fan), it must also be wired in hardware, e.g. by feeding the heater relay through the fan relay's output. That is the electrician's decision; the app is an extra layer.

### Inputs that switch relays and groups
- An input can control any number of relays and groups of its own board (`InputAction`, `InputActionsHandler`), each with its own action when it closes and when it opens: turn on, turn off or nothing. A relay in a group only through its group. A relay or group on another board is refused (across boards is issue #204), and `InputActionService` skips one saved before.
- `InputActionService` acts like a press of the button at that moment, with the input as the actor (`input:n`): a relay through `RelayControl` (with its auto-off), a group through `GroupSequencer` (in its order, with its run-on and auto-off). A relay already in that state is left alone (so one its schedule turned on stays the schedule's), unless the opposite command is still on its way (`ExpectedChanges.IsPending`); a group decides itself what there is to stop, and one fully on and idle isn't started again.
- Only a change the app saw as it happened acts: `BoardEventRecorder` hands it on (`InputChangeFeed`) once it is logged. A change noticed after a gap, or at start, does nothing. Without the board nothing is sent or queued.
- Each board's inputs' actions run on that board's own queue and loop, in the order its inputs changed: a board whose command doesn't finish holds up only its own inputs' actions, never another board's.
- Events name the input as who did it: "Door turned off the group Fan heater" (a dashed badge with "I").

### The board's own rules
- **A relay's state after a power cut is a setting the app may write** (Issue #516), not an own rule it may only turn off: `SetPowerOnAsync` sets any state the board has, `On` too, but only when a person saves it (or, for a group's relays, presses "Make it safe", "Create group" or Save; see Relay groups), never at a start, a connection or a reconnect. (Issue #27 planned it as an own rule of the kind `PowerOn`; that kind is dropped.)
- Rules on the board itself that switch its relays without the app (`BoardState.OwnRules`, see Boards), such as the VM201's timer programs. **The app never changes a board's own rules without a person's press**: it shows what it finds, warns, and turns them off only when a person asks. Nothing is sent to them at a start, a connection or a reconnect: the VM201's timers and the Waveshare (B)'s relay modes stay as they are until a person presses "Turn them off" or "Reset" (until issue #497 the app turned the VM201's timers off at the first connection, through `Vm201:DisableBoardTimers`, and set the Waveshare's modes to normal at each connection, through `Waveshare:ResetRelayModes`; those settings are gone, and one left in an installation's settings is ignored).
- `OwnRulesService` (`Features/BoardRules`) listens to every board through `BoardRegistry` (`StateChanged` and `OwnRulesChanged`), beside the safety services and never as one of their watchers, so they never wait for it. It keeps each board's latest state and does the database work on its own loop, and acts only when a board's rules differ from the last it saw. It never sends a command to a board.
  - A rule with no row gets a `BoardOwnRule` and is logged as `board-own-rule-found` by `system`, with the relay: `new` is true when this run had already read the board's rules without it (it was turned on while the app watched), false at first sight (at start, a new board, a new address). After a restart a rule that has its row logs nothing.
  - A row whose rule an actual reading no longer has is deleted, its "Keep" with it, without logging: if the rule comes back, the app warns again.
  - No reading (null rules: the board can't read them, hasn't answered yet, or its state was forgotten) changes no row.
  - A board's rows go with the board (`BoardRemoval`), with a new address (`BoardAddressHandler`) and with another model (`BoardRegistry.ReplaceModelAsync`): another board may be there. A board forgotten after its rules were read has its rows deleted by the service too.
  - It keeps each board's rows in memory for the screens, and raises `Changed` with the board's id when they change. A row's database save that fails is logged and tried again 30 s later.
- `OwnRulesHandler` (`Features/BoardRules`): `Warnings(boardId)` is the rules the board reports now that no person kept, and none until the service has read the board's rows, so a kept rule never shows as a warning just after the start. `TurnOffAsync` sends the board's `TurnOffOwnRulesAsync` at once and logs `board-own-rules-turned-off` by the person for the rules the board took; without a connection, or when the board doesn't take them, it says so in plain words and nothing is logged or queued. Their rows go when the board's next state no longer has them. `KeepAsync` sets `KeptUtc` and `KeptBy` and logs `board-own-rule-kept` by the person, once; a row deleted meanwhile (a new address, another model) says "The board no longer has that rule." and saves nothing. For the step while a board is added (see the setup guide): `ToAsk(boardId)`, the rules the board reports now that no person kept, also before the service has read the rows; `TurnOffAndConfirmAsync`, `TurnOffAsync` and then up to 5 s (`ConfirmWait`, on `TimeProvider`) for a state without them; and `KeepAllAsync`, which keeps them all in one save, making the row of a rule the service hasn't noted yet (logged as found, as the service would) under the service's own lock (`OwnRulesService.KeepReportedAsync`), so the service never inserts it too and logs nothing more for it.
- **Unavailable to Contactor.** A relay with an `InputLinkage` rule (`BoardState.Unavailable`, e.g. a Waveshare relay in linkage mode) follows its input, and the board ignores commands for it, so the app doesn't pretend it can switch it. `RelayControl` refuses it for a person, an input, a pulse and the API (`RelayUnavailableException`, before anything is sent or logged), and "All off" leaves it out, keeping its run and auto-off as for a refused relay. Removing its board leaves it as it is: the removal doesn't wait for it to go off, nor for a group's relay the interlock keeps on above it (`GroupPlanner.HeldOn`), and the confirmation says so, only when there is such a relay ("Relay 3 is controlled by the board itself and stays as it is.", "Relay 2 (Fan) stays on while relay 3 (Heat) is on."). The scheduler and auto-off skip it quietly, sending and logging nothing, tick after tick: a schedule's window still running and an auto-off that is due act at the first tick or check after a person resets it. It can't join a group (`GroupsHandler`: not among the free relays, "Unavailable to Contactor" in "New group", and a save refuses it as a new member). A group with such a member doesn't start (`GroupSequencer.StartGroupAsync` throws `GroupUnavailableException`, sending nothing; one member's ON is refused in words; the scheduler tries the start again quietly at each tick); it still stops as far as the board allows, and the interlock is planned on every status as ever. `BoardSequencer` sends no OFF and no ON to such a relay (only a stop's run-on ON goes), so nothing goes out again and again and no page is told to redraw when nothing changed; a stop whose OFF waits for such a relay that is on waits for it, as Stopping (saved in `GroupRuntime`, so also across a restart or a reconnect), without sending it again and without the 5 s timeout giving up or resending, while the interlock keeps what is above it on; its status line reads "Fan keeps running while Heat is on.". Once the board shows that relay off (e.g. its input turned it off), the stop carries on as usual: the run-on above it, then the rest. A change of the board's own rules alone wakes the sequencer too, so once the relay is reset the interlock acts at once. Its rule is never kept: no "Keep" for it anywhere (`OwnRulesHandler.CanKeep`), and "Keep them" while adding a board keeps the other rules only. "Reset" sets it back to normal through `OwnRulesHandler.TurnOffAsync`, logged as the person's `board-own-rules-turned-off` ("Erik reset relay 3"). Toggle and edge rules stay ordinary own rules, with "Turn off" and "Keep".
- **The auto-on of a relay in a group is never kept** (issue #532): the board would turn the relay on again without the group's order. `OwnRulesHandler.CanKeep(kind, inGroup)` is the one place that decides what may be kept: never `InputLinkage`, never `AutoOn` on a relay in a group, everything else. The board's card has no "Keep" for it and says in its place "Can't be kept: Heat is in a group, and the board would turn it on again without the group's order." ("Kan inte behållas: Värme ingår i en grupp, och kortet skulle slå på det igen utan gruppens ordning."), `KeepAsync` refuses it with those words, and "Keep them" keeps the other rules only; its warning stays until it is turned off. A keep is one conditional write in the database (`OwnRulesService`): it sets `KeptUtc` only on a row not kept yet and, for the kinds kept only outside groups (`OwnRulesHandler.KeptOnlyOutsideGroups`, derived from `CanKeep`), only while no group holds the relay, checked in the same UPDATE. So a person's "Keep" and another person's group save never cross: when the group comes first, nothing is written and the person reads the same "Can't be kept: …"; when the keep comes first, the group's save forgets it. When a relay joins a group (a group created, or one saved with a new relay), `GroupsHandler` forgets in the same transaction the "Keep" of each such rule on the board's grouped relays (`OwnRulesService.ForgetKeepsInGroupsAsync`), so the warning shows again, also after the relay leaves the group; it logs nothing. After a group is created, saved or deleted, `OwnRulesService.ReloadAsync` reads the board's rows again and raises `Changed`, so the screens follow. An auto-on on a relay in no group, and every other kind, keep their "Keep".
- Events name the board as the subject: "The board has its own timer for relay 3", "The board's own timer for relay 3 was turned on", "Relay 3 became unavailable: the board controls it itself", "Erik turned off the board's own timers for relays 3 and 5", "Erik reset relay 3", "Erik kept the board's own timer for relay 3", "The board turns relay 3 on again by itself after it goes off" ("… now turns …" when new). The auto-on reads as on the screens: "Erik stopped the board turning relay 3 on again by itself", "Erik let the board keep turning relay 3 on again by itself" (in Swedish "Erik gjorde att kortet inte längre slår på relä 3 igen av sig självt", "Erik lät kortet fortsätta slå på relä 3 igen av sig självt"). A turn-off's event names the rules the person asked for that the board took, and in `also` (each a relay and a kind, left out when none) the rules that went with them, as the board's rules before the command said: "Erik turned off the board's own timer for relay 3, and with it the timer for relay 5" ("… and with it the board turning relay 5 on again by itself"; "…, och därmed timern för relä 5"). Their rows go when the board's next state no longer has them, without another event. With two or more boards, its name ("Garage's own timer …"; in Swedish "Garages egna timer …", and no added s after a name that ends in s, x or z: "Lars egna timer …").

### External changes
- If `CMD_STATUS` shows a change the app didn't ask for (through the board's web GUI, the physical button or timers): log it with Actor `external`.
  - Implementation: keep a short list of "expected changes" per board (`LiveBoard.Expected`, by channel) that is cleared after 5 s; the OFF at the end of a pulse after the pulse's length plus 30 s (`RelayControl.PulseOffWait`).
  - Each board has its own recorder (`BoardRecorder`): its known state, disconnect clock, retry and contact times, and every event it logs has its board's id. Subscribed from the moment its live board is made, and running before the board's connection starts, so it handles every status in order.
  - A command that fails (refused, unreadable or no answer) logs nothing, and drops the expectation it added (`ExpectedChanges.Forget`), so a relay the board switched anyway shows on the next status as an external change instead of being taken for the app's own and lost. That holds for single relays, "All off", groups, auto-off and schedules alike. A relay the board didn't take in a command for several ("All off", a group's step) is treated the same when the board's state after the command (which holds what the command read) still shows it unswitched: "All off" doesn't log it or end its run, and its expectation is dropped. One the state shows switched went all the same, and counts as the app's. A group member's ON the board didn't take (sent alone or with other groups' commands) logs nothing and changes nothing in its group's run, and the person is told the board didn't do it.
  - A relay that comes on this way gets its own auto-off (see Auto-off), whoever turned it on. The setup guide's "Try" turns a relay off 2 s after a failed ON if the board shows it on, as the try promised only a moment.
- **A press the board didn't confirm** (no answer, an unreadable one, no connection): the relay's card (Relays) or status card (Relay) shows "The board didn't answer. The relay may or may not have switched." with **Try again** (the same command, sent at once, only while the board is online) and **Leave it**. It goes away when the person chooses or the board shows the relay as they wanted it. Nothing is guessed or queued.

### Connection
- A new installation has no board until the setup guide chooses one, and then may have no address for it yet (e.g. `Vm201:Host` empty): nothing connects, and no contact is lost, until one is saved (in the setup guide or on Settings). The board's live board waits for it (`LiveBoard.RunAsync`).
- When contact with a board is lost for more than 30 s, `connection-lost` is logged with that board's id, and `connection-restored` when it comes back.
- The UI shows a red warning: "No contact with the relay board. Since HH:mm. The states below may be wrong."
- **When the board says why it refuses the connection** (`BoardState.Problem`, see Boards), the screens say so in place of the general text, in the app's language (`BoardProblemText`, which picks "password" words for a board with a password alone and "login" words for one with a user name): another model ("The board at this address is an ETH484-B, not an ETH008-B.", or "… is another model, not the ETH008-B." for a model the app doesn't know), "The board asks for a password." ("… a user name and password."), or "The password is wrong." ("The user name or password is wrong."). The red box on Relays keeps its heading, and the line under it becomes that text with "See Settings."; the relays still wait for the board. The line for a board the filter hides is unchanged. A board that doesn't answer at all keeps the texts above. No secret is ever in these texts.
- **Before the board's first answer** since the app started (`BoardState.HasAnswered`) nothing is known: the warning reads "No contact with the relay board yet. Waiting for its first answer.", the heading leaves out "n of m on", and every relay, group and input card, and the status card on the Relay, Group and Input screens, is grey all over, with "Waiting for the board" and a dashed "–" in place of the ON/OFF button or the Open/Closed badge. Once it has answered, a lost contact keeps showing the last known states with the warning above. A new address (Settings or the setup guide) forgets the old board's state (`Vm201Client.SetEndpoint`, `BoardPoller.Forget`): it is unknown again until the board there answers, an answer from the old address still on its way is dropped, the changes the app just asked the old board for are no longer expected (`ExpectedChanges.Clear`), and `BoardEventRecorder` takes the new board's first status as at start, comparing no relays with the old board's. A new login keeps the states: it is the same board. The relays' and groups' runs (who turned them on, their auto-off, a schedule's catch-up) are kept: the app can't tell a new board from the same board at a new IP, and for the same board clearing them would leave a fan heater without its auto-off. For a new board this errs towards switching off.

## Identity (sign-in)

- **Every request goes through the chosen sign-in.** `SignInMiddleware` runs before anything that serves content, including static files and Blazor's SignalR connection. It asks the chosen sign-in method (`SignInChoice.Current`) who made the request. Nobody: answer 403 "Access denied.". An e-mail missing from `User` gets a new `User`, with DisplayName = the part before @, with a capital first letter.
- `/healthz` and `/setup/reload` need no sign-in and answer localhost only; in Development `/health` and `/alive` need none either.
- **Only from this network.** With "Only on this network" as the way in, and in setup mode (whatever the way in), `SignInMiddleware` first asks `ThisNetwork`, before the sign-in or `SetupMode`. It answers a request only when the connection's own address is on a local network: 10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, ::1, fe80::/10 and fc00::/7. An IPv4 address given as IPv6 (`::ffff:a.b.c.d`) counts as that IPv4 address. A request without an address is refused too, as `ThisMachine` refuses it. Forwarded headers (`X-Forwarded-For`, `Cf-Connecting-IP` and the like) are never believed. Carrier NAT (100.64/10) is not this network.
  - The app never uses ASP.NET Core's forwarded headers (`UseForwardedHeaders`). At start it refuses to start when `ASPNETCORE_FORWARDEDHEADERS_ENABLED` (the configuration key `ForwardedHeaders_Enabled`) is "true", in any case, as ASP.NET Core reads it (`ForwardedHeadersCheck`): with it on, anyone could write a made-up address in `X-Forwarded-For`. It logs an error and stops with "Forwarded headers are on (the setting ForwardedHeaders_Enabled, e.g. ASPNETCORE_FORWARDEDHEADERS_ENABLED). Contactor reads the visitor's address itself; turn the setting off." The demo's proxy is its own program: it takes only `X-Forwarded-Proto`, and only from the tunnel.
  - Anything else gets 403, plain text, "Contactor can only be opened on its own network.", and the log gets a warning with the address at most once a minute (`OutsideWarningInterval`, `TimeProvider`): the app's port can be reached from the internet, and must be closed in the firewall or router.
  - Cloudflare and Tailscale reach the app from loopback inside its container, so the check doesn't stop them; with them as the way in, their sign-in alone decides. The demo's copies are reached from 127.0.0.1 too.
  - On a cloud server, set up through an SSH tunnel (`ssh -L 8080:localhost:8080`), which arrives from this machine.
  - A safety net, not the fence: Docker's published port keeps an IPv4 visitor's address, so `install/compose.yml` publishes it on IPv4 only (`0.0.0.0:8080:8080`). On IPv6, and with rootless Docker, Podman or Docker Desktop, the visitor arrives from a private address of Docker's, and the check lets them in.
- **The sign-ins** (`SignInCatalogue`):
  - "Cloudflare Access" (`cloudflare-access`, `CloudflareAccess`): see below.
  - "Tailscale identity" (`tailscale-identity`, `TailscaleIdentity`): see below.
  - "No sign-in" (`none`, `NoSignIn`), "Not recommended" in the guide: every request is let in as one shared person, `someone@contactor.invalid`, whose name is "Someone". The events can't tell people apart.
- **The sign-in must fit the way in.** Each way in lists the sign-ins it works with: "Only on this network" only No sign-in, Cloudflare only Cloudflare Access, Tailscale only Tailscale identity. So No sign-in is never used with a public link. The guide offers only what fits, and at start the app refuses a saved sign-in that doesn't fit its way in, or has no way in (`CheckSignInFitsWayIn`); the message says to run `reset-sign-in`.
- **Setup mode:** while no sign-in is chosen (`Installation.SignInType` empty), nobody is signed in, and `SetupMode` lets through only the static files and the setup code's page (`/setup/code`). A browser with the setup code's cookie also gets the guide (`/setup`) and Blazor's connection (`/_blazor`). Any other GET goes to the code page (or the guide once the code is typed); any other request gets 403. An empty database always starts this way, also in development.
- **The setup code** (`SetupCode`): 8 letters and digits without look-alikes, shown as `ABCD-EFGH`. A new code is made at each start without a sign-in, and when `reset-sign-in` clears the sign-in. It is kept in memory only and written to the log. Case, spaces and dashes don't matter. The right code gives the browser the cookie `contactor-setup` (HttpOnly, SameSite Lax, Secure over HTTPS), signed with data protection and tied to the current code, so a new code ends it. After 5 wrong codes in a row, no code is tried for a minute; a new code doesn't reset that count.
- **Locked out:** `docker exec contactor dotnet Contactor.Web.dll reset-sign-in` (`SignInReset`) clears `Installation.SignInType` and calls `POST /setup/reload`. That reads the sign-in again and makes a new setup code only when the sign-in has just gone; it returns nothing. The guide then opens again at "How do people sign in?", or at "How do people reach the app?" for a Cloudflare installation without a saved address (one set up with environment variables), which asks for the tunnel's address first; an empty token keeps the saved one. The way in (so the tunnel keeps running), the board, the relays, the events and the schedules stay. When the app isn't running, it writes a code when it starts.
- **Demo:** `Contactor.Demo` gives each visitor of the public demo their own copy of the app and the simulator, as processes on 127.0.0.1 behind its proxy, and deletes the copy when it ends. It runs from `/opt/contactor-demo` with `deploy/demo/compose.yml`, started and upgraded with `docker compose`; see [`DEMO.md`](DEMO.md).
- **Cloudflare Access:** validate `Cf-Access-Jwt-Assertion`: RS256, `aud` against the Access application's AUD tag, `iss` against `https://<TeamDomain>`, lifetime against `TimeProvider`. Missing or invalid JWT: denied.
  - **The settings** come from `CloudflareSettings`: what the setup guide saved (`CloudflareSetting`), else `CloudflareAccess:TeamDomain` (the host name only) and `CloudflareAccess:Audience` from the configuration. They are read at each request, so a change takes effect at once. The team domain must end in `.cloudflareaccess.com`, with one label before it: the app fetches its keys from there, and whoever controls that domain decides who may sign in. The app doesn't start while Cloudflare Access is the sign-in and its settings can't be used.
  - **The e-mail comes from the JWT's `email` claim**, not from the `Cf-Access-Authenticated-User-Email` header: the claim is signed, the header isn't.
  - The JWKS is fetched from `https://<TeamDomain>/cdn-cgi/access/certs` and cached for 1 h. A JWT with an unknown key refetches the list at once, at most once a minute. A request with no keys to use (the first fetch, or a new team domain) waits for the fetch; one with keys goes on with them while they are fetched again. A fetch gives up after 30 s. A failed fetch keeps the keys it had, and counts as a fetch; without keys everyone is denied. A new team domain drops the old team's keys once its own are fetched.
- **Tailscale identity:** the person is the login in `Tailscale-User-Login`, which Tailscale Serve puts on each request it passes on. Serve removes any copy of that header a client sent itself, and sends none for tagged devices or through Funnel: denied.
  - **Only through Serve.** The header is believed only on a request that came in on the app's address for Serve (the connection's own end), which only the container itself can reach. Not on one from 127.0.0.1: tailscaled passes connections from the Tailscale network there, past Serve, so anyone on that network could write the header.
  - The login is plain ASCII, or RFC 2047 encoded words (`=?utf-8?q?…?=`) for other characters, which are decoded; encoded words that decode to plain ASCII aren't Tailscale's and are refused. It is usually an e-mail address; a GitHub login looks like `name@github`. Anything else: denied.
  - The guide takes Tailscale identity only once the app is on the Tailscale network, since it sends people to its address there.
- Blazor Server: the middleware sets `HttpContext.User`, which Blazor carries into the circuit when it starts. Components read the user through the scoped `CurrentUser` (built on `AuthenticationStateProvider`), since headers are gone in the SignalR circuit afterwards. It is null only for a setup connection, let in by the setup code.

## Operations

- **Versions:** `YYYY.M.D` in UTC without leading zeros, plus `.N` for a later release the same day (`scripts/release-version.sh`). A release is built with `-p:Version=<version>`; every other build is `0.0.0-dev` (`Directory.Build.props`). `AppBuild` reads the version and commit; they show in `/healthz`, the start log, the image label `org.opencontainers.image.version` and at the bottom of Settings.
- **Publish:** the Release workflow (started by hand) builds the solution and runs every test (a failure publishes nothing), builds and pushes the image from the `Dockerfile` with `docker buildx` (`scripts/images-build.sh`), tags it `YYYY.M.D[.N]`, `latest` and `sha-<commit>`, signs it with cosign by digest (`scripts/images-sign.sh`, keys in `deploy/cosign/`) and tags the commit `v<version>`. The demo's image (`ghcr.io/gonace/contactor-demo`, from `Contactor.Demo/Dockerfile`) is published and signed the same way with the same version, next to the app's (the workflow's `publish` matrix); the commit is tagged only when both succeeded.
- **Install:** `install/install.sh`, the only file the Release workflow attaches to each GitHub Release (with the release's tag filled in, shown on its first line), run as `curl -fsSL https://github.com/gonace/Contactor/releases/latest/download/install.sh | sh`. It asks nothing: it checks Linux, arm64 or amd64 and the free disk space (stops below 2 GB, warns below 5 GB), installs Docker if it is missing, pulls `ghcr.io/gonace/contactor:latest` (or the image an existing `compose.yml` names) only when it isn't on the machine already, checks its cosign signature by digest as the helper does (the same two public keys, in its own `COSIGN_KEYS`; `scripts/images-sign.sh --check` makes sure both copies have them; an image that isn't signed stops it with nothing changed, a check that can't run, e.g. without a connection, says "Couldn't check the signature (no connection?)", and either way an image this run downloaded is removed again, also when the script is stopped during the check), puts that image's `compose.yml` and `data/` (owned by 1654) in `/opt/contactor`, starts the app on exactly that digest (port 8080, on IPv4 only, `/opt/contactor/data` as `/data`, no settings), waits up to 2 minutes for its health check, and puts the update helper in place (not on a machine without systemd, or without `setpriv` and `flock`: then it says "Update now" isn't available). The image carries `compose.yml` (`/app/install`) and the helper with its units (`/app/updater`), all from `install/`: nothing else is downloaded. The script reads them as the helper does: from a container made from the image and never started (`contactor-install-read`, `--pull never --network none`, removed with its volumes afterwards) into a root-only temporary folder; each must be a regular file, not empty, with the line it starts its part with (`services:`, `HELPER_VERSION`, `[Unit]`) and the word `contactor`, and the helper must pass `bash -n`; each goes in with one `mv`. A file the image doesn't have and a copy that fails are told apart: an image without `compose.yml` stops a new installation as too old, a failed copy says to check Docker and the free disk space, a broken file stops it; each with nothing changed. Run again while the app runs, it takes the helper from the image the app runs, once that image's signature is checked the same way (one that isn't signed, can't be checked, or has no published digest, e.g. one built on the machine, leaves the helper in place and says so): no Contactor image is pulled, tagged or removed (only the cosign image may be pulled, when it isn't there yet), and a helper with a lower `HELPER_VERSION` than the one in place never replaces it (a unit that is missing is still put back). An image without a helper leaves the one in place; with no helper in place (a machine installed with 2026.11.15.1, whose image has none), it says to run the install command with `--uninstall` (the data is kept) and then again; when the container restarts or stops, or its health check fails, it stops with the last 20 lines of `docker logs`. Then it shows the address and, while no sign-in is chosen, the setup code: the last `SetupCode` log line in `docker logs` since the container started. `dotnet /app/Contactor.Web.dll setup-status` (`SetupStatus`) tells it how far the setup is, from the database: `setup-code` (no sign-in), `setup-guide` (a sign-in, the guide not done) or `done`, with the saved Cloudflare address or Tailscale's name on a second line. It is asked only in an image whose `org.opencontainers.image.version` is a release after 2026.11.15 or `0.0.0-dev`: an older app doesn't have the command and would start a second time in the running container. With an older image the script shows the address and the setup code from the log only. The app refuses a first argument that is neither one of its commands nor an option (`AppCommands`), so a command it doesn't have never starts it. Run again, it repairs only what is missing and changes nothing that works. `--uninstall` removes the container, its image, `compose.yml` and the update helper (with the `.previous` copies it keeps), and keeps `data/`; `--delete-data` removes that too. While Docker is installed but doesn't answer, `--uninstall` changes nothing. It refuses to run while the helper is updating.
- **Run:** Docker Compose on the Raspberry Pi (Raspberry Pi OS Lite 64-bit on an SD card, an endurance card recommended), from `/opt/contactor` with `compose.yml`. One container, run as the image's user 1654; `/opt/contactor/data` is mounted as `/data` (database, `backups/`, `keys/`) and owned by it. `cloudflared` is pinned by digest in the `Dockerfile` and, with Cloudflare as the way in, runs a remotely managed tunnel: `<your hostname> → http://contactor:8080`.
- **Update now** (Issue #232): the app never gets the Docker socket. The update helper on the host does the update: `install/contactor-updater.sh`, installed by `install.sh` as `/usr/local/sbin/contactor-updater` with `contactor-updater.service` (a oneshot, run at every start and when asked, so one runs at a time) and `contactor-updater.path` (starts it when `data/updates/request` appears); running `install.sh` again brings them up to date ("Update helper installed"), and `--uninstall` removes them. The image carries copies of the three (`/app/updater`, from `install/`), which `install.sh` puts in place: after a healthy update the helper brings itself and its units up to date from them (Issue #325), so a fix to the helper or a new signing key reaches the machine without the install command. It reads them from a container made from the new image, by the digest it checked with cosign, and never started: never from the running app, `/data` or a download. Each file goes in only when it differs and passes its check (the helper: a regular file, not empty, with a `HELPER_VERSION` line no lower than the installed one, that `bash -n` reads; a unit: a regular file, not empty, with a `[Unit]` line and the word `contactor-updater` in it; a unit that fails is skipped, the helper still goes in), in one step (a new file in the same folder, then `mv`), with the copy before kept as `<file>.previous`; then `systemctl daemon-reload` if a unit changed (the service may write `/usr/local/sbin` and `/etc/systemd/system` for this). The new helper runs from the next run on: `mv` leaves the running one's file alone. A helper that fails its check changes nothing, units included, and the update still counts as done; an image without the copies (releases before them) changes nothing either. A helper from before this change brings nothing: such a machine runs the install command once after an update to a release with this change. The trade-off: whoever holds a signing key and can push to `ghcr.io/gonace/contactor` can get root on every machine that then presses "Update now", so a leaked key is rotated before the next release (`deploy/cosign/README.md`); a rotation can't undo a helper already replaced. The app and the helper talk only through `/data/updates` (`UpdateFolder`): the app writes `request` ("update", or "cancel" until the restart); the helper writes `status` (`key=value`: `id`, `state` running/done/went-back/failed/current, `step`, `from`, `to`, `reason`, `started`, `changed`), `helper` (so the app knows it is there), `logs/update-<id>.log` (the latest 10) and asks the app for `before-update.db`. The app's user owns that folder, so the helper (root) treats it as untrusted: it reads and writes it only as that user (`setpriv`), takes nothing from it but the request's first word (read only from a regular file, at most 16 bytes, within 5 s, so a FIFO, a link or a device can't hold it; anything else at `request` is removed, and one it can't remove makes it wait a minute rather than start again at once), ignores a request older than 2 minutes, and any request on its first run after the machine starts (by the kernel's boot id: a Pi without a clock can't tell a request's age then; the app also takes back one the helper didn't take within 30 s: nothing is left for later), and always updates to the newest release, `ghcr.io/gonace/contactor:latest`, never to an image, tag or command a file names. Its steps: the free disk space (the image, the backup and 200 MB, on the fullest of Docker's folder, containerd's and the data); pulling the running version's digest (so Docker's containerd image store keeps it) and `latest`, then putting `latest` back on the running version at once, so it only ever names a checked image ("cancel" stops the `docker pull` itself, waits until it is gone, and puts `latest` back); nothing newer than the running version: `current`; cosign by digest with the keys in its `COSIGN_KEYS`, copies of the public keys in `deploy/cosign/` (an unsigned image is removed); `docker exec … update-backup` (`UpdateBackup`: `VACUUM INTO` `updates/before-update.db`; while a group is starting or running on it copies nothing and exits with 3, and the helper shows "waiting" and asks again every 10 s (logging the wait once), for up to 10 minutes, then stops with nothing changed: `failed`/`switching`); then, past the point of no cancel, `docker compose up` on exactly that digest (`CONTACTOR_IMAGE=…@sha256:…`) and up to 5 minutes for its health check. Healthy: `latest` names it, and the app's older images are removed but the one before (to go back to). Not healthy, stopped or restarting: the new version's last 200 log lines go into the log, the app is stopped, the database backup put back (its `-wal` and `-shm` removed first), and the version before started again by its digest: `went-back`. What it needs to finish or go back is in `/var/lib/contactor-updater/journal` (root only): after a power cut, the next start finds it and finishes the update or goes back; one cut before the restart is `failed`/`interrupted`. Secrets never get in the log: the helper doesn't log the container's settings, and every line goes through `strip_secrets` (tokens, keys, `password=`…), which `UpdateLog.Strip` repeats before the app shows or sends a log. `scripts/updater-test.sh` tests it with Docker, a local registry, a test key and stand-in images: a good update, one that never gets healthy, an unsigned image, power cuts before the restart and during the check, requests that must do nothing, and the helper bringing itself up to date (a newer one, one that fails its check, the same one, an older one, none, and files planted in `/data` or the running container), and `install.sh` (an image that isn't signed refused with nothing changed; a signed one installed by its digest, with `compose.yml` and the helper from it; run again, the helper from the running image once its signature is checked and with nothing pulled, tagged or removed, never from an unsigned one or an image without a helper, never an older helper but missing units put back; a check that can't run, and one stopped with Ctrl-C, removing the image it downloaded; an image without `compose.yml`; a failed copy; nothing downloaded with curl or wget). The app (`UpdateService`) reads GitHub's public releases list once a day, and on "Check now" at most once a minute, without a login (`Updates:ReleasesUrl`, saved in `updates/releases.json`; drafts, pre-releases and other tags left out), follows the status (every second while an update runs, every 5 s otherwise), shows the splash from the restart on, treats a status that hasn't changed for 15 minutes from the restart on (an hour before it) as a helper that stopped (the splash goes then, as each poll re-checks it), and logs each update, also one that found nothing newer. The helper always looks in `/opt/contactor/data/updates`, the container's `/data/updates`: `Updates:Folder`'s default with the database at `/data/contactor.db`. `install.sh` refuses to run, and `--uninstall` too, while the helper holds its lock (`/var/lib/contactor-updater/lock`) or its service is activating. The Release workflow attaches only `install.sh` to each release (Issue #346): the helper and its units come from the image. It makes each release with notes from the merged pull requests' titles, those labelled `internal` left out (`.github/release.yml`), and an Images section at the end: each image's version, digest, package page and `docker pull` line by digest (Issue #314).
- **Migration:** run `Database.Migrate()` at start.
- **Backup:** every night at 02:30 the app copies the database with SQLite's `VACUUM INTO` into `backups/contactor-YYYY-MM-DD.db` and keeps the latest 14 (`Backup:Folder`, `Backup:Keep`, `Backup:At`). Right after it, the events older than a year are removed (see [Data model](#data-model-sqlite)), also when the copy failed; a failure of either is logged, and both run again the next night.
- **Health check:** `/healthz` (localhost only, otherwise 404) returns 200, also while a board has no contact, with the boards' connection status: each board in `boards` (`id`, `name`, `model`, `connected`, `lastContactUtc`), and, kept from when the app ran one board, `boardConnected` (every board connected; false while there is none) and `boardLastContactUtc` (the oldest contact; null while a board has had none). The image has no shell or curl; `dotnet /app/Contactor.Web.dll healthcheck` asks it and exits 0 or 1, and compose uses that.
- **Locked out:** `docker exec contactor dotnet Contactor.Web.dll reset-sign-in` forgets the sign-in, and the setup guide opens again behind a new setup code in the log (see [Identity](#identity-sign-in)).
